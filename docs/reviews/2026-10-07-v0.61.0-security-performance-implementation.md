## SEC-061-01: PNG resource bound

`native/qt/maptiles.cpp` now validates signature, chunk framing, lengths, CRCs,
256×256 IHDR and final IEND without decompression before constructing a
`QImageReader`. Direct byte comparisons avoid signature/chunk-name allocations
as well; no per-chunk buffer is constructed. It admits pixel data and bounded uncompressed PLTE, tRNS, sRGB,
gAMA, cHRM, sBIT and pHYs chunks. Text, compressed ICC profiles, EXIF, unsupported
chunks and trailing bytes are rejected. ICC-tagged tiles are deliberately
unsupported; ordinary RGB/RGBA/palette transparency and basic color information
remain supported. The existing 128 KiB encoded and 512 KiB pixel bounds remain.
Only the same admitted bytes reach QML's second decoder. No decoder threading,
redirect, generation, cancellation, cache or concurrency controls were weakened.

New Qt fixtures cover multiple 4 MiB compressed texts, compressed international
text and profiles, plain text/EXIF, malformed CRC/length/trailing data and
RGB/RGBA/palette tiles. Each exercises sixteen simultaneous replies. Existing
teardown/reentrant-cancellation tests remain, and the new policy tests also run
under ASan/UBSan/leak detection.

The separate-process `packaging/test_map_png_budget.sh` enforces a generous
64 MiB process RSS threshold and repeats each input sixteen times. Measured:
plain 944-byte RGB accepted at 21,904 KiB; original-equivalent 17,380-byte text
fixture rejected at 19,384 KiB; international text rejected at 19,400 KiB;
profile rejected at 19,396 KiB. These final results are in `png-budget-final.log`. The audit's accepted metadata fixture peaked at
115,872 KiB. These are process RSS, including Qt overhead, not decoded pixel
storage. A valid reply still has the existing ≤512 KiB pixel allocation; at most
sixteen bounded replies are active. The preflight does linear work over at most
128 KiB per reply and allocates no expanded metadata.

## REL-061-01: delivered freshness transitions

`mapSince` tracks the small derived status key under the app mutex. Status
changes advance map revision, including clock rollback and data more than five
minutes in the future. Unchanged revisions return before constructing labels
or encoding the 25-cell lattice. The service's existing tick cadence delivers
stale status after twenty minutes and removes payload after six hours; it does
not send unchanged maps on each tick. Existing inclusive freshness boundaries
are preserved. Hidden maps remain closed, and reopening delivers current state.

budgets/cancellation remain intact. `TestMapFreshnessEvents` covers exactly one
necessary event per transition and no duplicate unchanged tick events. Existing
map request-budget and hidden/reopen cancellation tests also pass.
